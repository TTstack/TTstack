TTstack — Lightweight Private Cloud

A small VM and container manager for developers and small teams. Create temporary or retained environments on your Linux hosts, reach them over SSH or published ports, and manage their lifecycle from one controller.

Linux x86_64 is the supported host platform. Mixed fleets can also use experimental FreeBSD bhyve and Jail with manual setup.

One controller, one agent per host, and no extra infrastructure in between.

Create, use, tear down

Start with a registered host and a prepared alpine-cloud image. This example keeps the environment until explicit deletion. The SSH address is illustrative: configure the agent's client-reachable address, then use the endpoint reported by env show. 

$ tt env create demo --owner dev --image alpine-cloud \
    --engine qemu --cpu 1 --mem 256 --disk 2048 \
    --ssh-key ~/.ssh/id_ed25519.pub --lifetime 0
$ tt env show demo
# Selected output; VM and access rows omitted:
Environment: demo
  Owner:   dev
  State:   Active
  VMs:     1
  Expiry:  never (retained until explicit deletion)

# Use the reported SSH endpoint when ready:
$ ssh -p 20000 root@192.0.2.10
$ tt status
Fleet Status
  Hosts:   2/2 online
  VMs:     3
  Envs:    2
  CPU:     8/64 cores
  Memory:  6144/131072 MB
  Disk:    122880/4000000 MB

Capacity figures are configured reservations, not measured host load; the CLI labels memory and disk as MB, with values in MiB. On the agent host, use the guest IP directly: VM port forwarding does not provide loopback access. Initial SSH, public endpoints and readiness are described in the SSH guide. The full walkthrough, including host registration and image creation, is in the README quick start.

Lifecycle

Environments and their VMs move through a small, explicit set of states.

  • Stop keeps the disks, not the memory. Stopping releases execution resources and preserves disks or containers; starting boots the workload again. Save work in the guest before stopping.
  • Delete is destructive. Deleting an environment removes its runtime disks and containers. Cleanup that does not finish stays visible as deleting and is retried.
  • Expiry is a cleanup trigger. The default lifetime is six hours. Choose a longer lifetime, or use --lifetime 0 to disable automatic expiry. When a lifetime ends, the controller runs the deletion cleanup path — it is not an exact termination deadline.

Linux engines, one interface

QEMU/KVM

Full VMs from cloud images, with initial SSH accounts/public keys and optional guest sudo. CPU/RAM updates and virtual-disk growth are supported while stopped; the guest manages partition and filesystem growth.

Guest images and access →

Firecracker

MicroVMs under jailer with per-VM resource limits, a prepared kernel and rootfs, prepared-image SSH and offline ext4 growth. Shutdown is requested before forced termination; the built-in smoke image does not include SSH.

Firecracker setup →

Docker/Podman

Containers from images that provide a long-running default command, publishing the application ports you ask for. Runtime selection is bound to the agent inventory; installing another runtime does not switch it.

Container images →

Experimental FreeBSD

bhyve boots prepared raw disks and supports stopped zvol backups; Jail uses copied roots with optional root public keys. Neither supports offline resizing or Linux guest network isolation. Native binaries and manual host/network setup are required. FreeBSD scope and limits →

Highlights

What the lifecycle machinery does on its own, and the choices that keep the stack small.

Inspect capabilities before creation

tt capabilities shows engine/storage support; tt host show HOST_ID explains host availability and denial reasons. Placement, direct agent requests and dashboard controls share the same capability contracts. Offline reports remain visible as history.

Technical capabilities →

Opt-in disk recovery points

Back up stopped QEMU/Firecracker root disks on qualified ZFS or reflink storage, or experimental bhyve root zvols. Restore overwrites the current disk and leaves the VM stopped. There is no full-copy fallback; environment deletion and expiry also remove its backups.

Disk backup and restore →

Expiry and deletion retries

Choose a lifetime or keep an environment until you delete it. When expiry is enabled, the controller cleans up expired environments and retries incomplete deletion.

Recovery semantics →

Persisted before it runs

Creation plans are saved before provisioning. A timeout or disconnected client can leave running or partial resources; inspect the existing name before retrying.

Lifecycle reconciliation

Agent and controller reconcile on a loop: failed network restoration is retried and confirmed process state clears obsolete recovery errors. Uncertain resources remain available for inspection. Reconciliation yields between VM checks so queued lifecycle operations can proceed.

Placement by reservation

VM placement prefers eligible ZFS zvol hosts and falls back to file storage. Scheduling uses the CPU, memory and disk you reserved, not measured load, so placement stays predictable.

Guest network controls

Both Linux QEMU and Firecracker support blocking routed outgoing traffic while allowing replies to inbound connections. Separate opt-in isolation blocks guest-initiated access to host services, peers and private networks. These controls are unavailable for Docker/Podman.

Networking and isolation →

Disks that survive a stop

Stopping releases execution resources but preserves disks and containers; VM memory does not survive. ZFS zvols with snapshot clones, and file-backed disks, sit behind the same interface.

Resize a stopped VM

QEMU and Firecracker support CPU and memory increases or decreases for the next boot, and disk growth while stopped. QEMU guests manage their own filesystem growth; Firecracker also grows ext4 offline. Resource updates are unavailable for Docker/Podman, bhyve and Jail.

Offline resource updates →

One controller, three interfaces

No message queue and no database server: the controller and each agent keep their state in SQLite, and you drive the fleet from the CLI, the REST API or the web dashboard. The dashboard supports basic SSH-key input and host capability inspection; custom SSH accounts, guest configuration, resize and disk backup are available through the CLI and API.

One workspace, your hosts

tt, tt-ctl, tt-agent and the shared core are a single Rust workspace. Linux and experimental FreeBSD builds select their native host implementations while sharing fleet models.

Supported scope, defaults and recovery semantics live in compatibility and the API reference, with the detailed contracts and limitations for each engine.

Scope and access

  • Small Linux fleets. Linux x86_64 is the supported host platform. The 50-host and 1000-VM limits are guardrails, not benchmarked capacity.
  • Experimental FreeBSD in mixed fleets. Native lifecycle tests cover FreeBSD 15.1-RELEASE-p3 amd64 alongside two Linux hosts. Primary CI and automated deployment remain Linux-only; this does not establish support for other FreeBSD versions or untrusted-tenant isolation.
  • One administrator boundary. Deployment configures a shared API key. Owner labels are not authorization, and services use HTTP without built-in TLS. Manual starts without a key leave the API unauthenticated. Keep management access on a trusted network or protected proxy.
  • Explicit operator responsibilities. Images are prepared on each host. There is no image distribution, guest migration, HA, cross-host private network or automatic guest restart after a host reboot. Identity and application policy belong to callers.
  • Evidence has a scope. Implemented options and native-engine probes are not blanket live-validation claims. See the compatibility matrix and dated reports.
