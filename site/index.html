TTstack — Lightweight Private Cloud

A tiny private cloud for developers and small teams. Create temporary VMs and containers on hosts you own, reach them over SSH or published ports, and stop, restart or delete them reliably.

One controller, one agent per host, and no extra infrastructure in between.

Lifecycle

Environments and their VMs move through a small, explicit set of states.

  • Stop keeps the disks, not the memory. Stopping releases execution resources and preserves disks or containers; starting boots the workload again. Save work in the guest before stopping.
  • Delete is destructive. Deleting an environment removes its runtime disks and containers. Cleanup that does not finish stays visible as deleting and is retried.
  • Expiry is a cleanup trigger. Environments expire on their lifetime, and the controller then runs the same cleanup path — it is not an exact termination deadline.

Highlights

What the lifecycle machinery does on its own, and the choices that keep the stack small.

Automatic lifecycle management

Environments expire on their own lifetime, and the controller then runs cleanup on a loop — retrying what failed instead of forgetting it.

Recovery semantics →

Persisted before it runs

A create request is saved before any work starts, so a timeout or an interrupted client never loses it. Inspect the name before you retry.

Self-healing reconciliation

Agent and controller reconcile on a loop: failed network restoration is retried, late readiness clears stale errors, and process recovery uses its own markers rather than deleting disks.

Placement by reservation

VM disks prefer eligible ZFS hosts and fall back to file storage. Scheduling uses the CPU, memory and disk you reserved, not measured load, so placement stays predictable.

Jailed, limited, isolatable

Firecracker runs under jailer with per-VM resource limits, and guests can be denied outgoing traffic or isolated from the host network.

Isolation setup →

Disks that survive a stop

Stopping releases execution resources but preserves disks and containers; VM memory does not survive. ZFS zvols with snapshot clones, and file-backed disks, sit behind the same interface.

Resize a stopped VM

CPU, memory and root disk can be changed on a stopped Firecracker VM — grow-only, applied when it boots again.

Offline resource updates →

One controller, three interfaces

No message queue and no database server: the controller and each agent keep their state in SQLite, and you drive the fleet from the CLI, the REST API or the web dashboard.

One workspace, your hosts

tt, tt-ctl, tt-agent and the shared core are a single Rust workspace, running on Linux x86_64 hosts.
